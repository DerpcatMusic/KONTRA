# Compatibility implementation checklist

This checklist describes implementation boundaries, not a guarantee that an imported instrument sounds or behaves like Kontakt. The broad support summary remains in the [README](../README.md#compatibility-and-known-gaps). No area here is certified as complete.

## Source, validation and released builds

Reviewed development source: `8883c4e`, 2026-10-02. Changes after the previously validated source baseline still require the combined release-profile test batch and platform builds. A source change, an isolated passing test and a published nightly are separate milestones. Check a downloaded artifact's build identity and `release-manifest.json`; this document does not assert that development changes are already available in that artifact.

- **Implemented, partial:** a code path exists; its stated limits still apply.
- **Integrated, validation pending:** present in the reviewed development source; the combined validation/release gate remains open.
- **Candidate, validation pending:** isolated work awaiting integration or required checks; unavailable in the reviewed source.
- **Open:** unsupported semantics, an unverified interpretation, or missing reference evidence.

Targeted checks validate their exercised behavior. They do not establish arbitrary file compatibility, every script action, live-host deadlines or Kontakt sound equivalence.

Before a pending behavior becomes a compatibility claim:

- [ ] Reproduce its causal record, service call or authored interaction; distinguish unsupported semantics from missing or malformed input.
- [ ] Fix the shared importer/runtime/DSP path and retain honest failures on unsupported inputs.
- [ ] Run a focused check that fails without the change, including stale-source/boundary handling where applicable.
- [ ] Check real audio/state/control results, rather than only parsing, successful catalog enumeration or warning removal.
- [ ] Verify bounded work and zero render-thread heap operations for changed callback/processing paths.
- [ ] Run the combined release-profile checks and native platform builds before publishing an artifact.
- [ ] For sound-equivalence claims, compare matching reference renders; for host claims, exercise the actual host/device workflow.

See [CI and snapshot checks](CI.md) for the release gate. Public documentation should contain generic behavior and code references; support bundles, source scripts, access data and proprietary assets stay outside the public repository.

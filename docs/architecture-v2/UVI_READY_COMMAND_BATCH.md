# UVI commands and UI publication

The ordinary script owner previously completed a full UI export before taking
and sending commands already generated by its callbacks. A large interface
could therefore hold a ready note behind unrelated picture/control projection.

The current acknowledged Pizzicato witness used inspector binary SHA-256
`f1721026361e5b41f86d64e035de71003767bfc5d7e6093c4d4ab8784e560cf3`.
Its note observation saw UI export at 1.127 ms with no commands drained, then
13 drained commands at 155.373 ms; the full publication acknowledgement took
155.410 ms. These are sampled wall observations, not exact command generation
timestamps or native Falcon latency measurements.

| Completed owner work | Wall ms | Caller-thread CPU ms |

| Initial UI snapshot | 196.805 | 195.379 |
| 15 UI publications | 2,416.678 | 2,409.912 |

| Command pushes across 3,565 turns | 3.387 | 1.687 |

There were zero command-queue backpressure retries. Interface export accounted
for 99.25% of publication CPU. Across all 16 exports, including the initial
snapshot, widget conversion used 2,375.467 ms CPU and topology used 170.912 ms.
These export substages overlap the rows above and must not be added to them.

## Bounded ready batch

After ordinary callback/advance processing, the worker may transfer its entire
already-generated command batch before UI export. Every command must be one of
Play, Release, Modulation, Change, Fade, Midi or Parameter, and the whole batch
must fit the queue's initially observed free slots, at most 1,024. Any unsafe
command, pending convolver rebuild or insufficient space leaves the entire
batch untouched for the original collector. There is no deliberate split at a
queue boundary or around an insert command.

This early operation executes no Lua, rebuilds no impulse and waits for no
queue space. Sent commands remain charged against the existing 65,536-command
admission limit until the ordinary collector completes its stale-impulse
rebuild. Getter-generated later commands still follow the ready batch. The
ordinary late collector, blocking FIFO drain and backpressure UI service remain
in place. A completely full audio queue therefore cannot newly block UI
publication before that existing drain.

The diagnostic acknowledgement and its ordered drain marker still follow the
complete UI/fault publication and late commands. A ready voice can sound while
that acknowledgement is pending. Seeded audit owners retain their existing
barrier path. Audio-side event submission, command draining and DSP rendering
receive no new scans, clocks or allocations from this change; the new work and
optional phase clocks run on the script owner.

## Validation and limits

Authored fixtures hold publication of a 10,001-widget interface while a real
core runtime consumes the ready note and renders nonzero PCM. After releasing
publication, they compare the entire Interface, control value, callback count,
fault state, saved state and PCM exactly with an inline owner. Other fixtures
cover zero/partial queue space, every position of unsafe commands, a full queue
without an audio consumer, later getter-generated commands, the unchanged
convolver rebuild boundary, command-capacity findings/reset, owner shutdown
and seeded audit behavior.

The final serialized `sampler-uvi --lib` checks passed under the `ci` profile:
156 passed and 10 ignored with default features; 166 passed and 10 ignored
with `scan`. Both ran with `--locked --offline -j2 --test-threads=1`.
The scan suite also retains explicit coverage assertions for approximated
SparkVerb and an independently unmodeled insert; no production coverage
classification or warning was changed. Logs are retained privately under
`PluginArtifacts/kontra-diagnostic-fixes/uvi-ready-batch-20261015/` as
`default-lib-final.log` and `scan-lib-final.log`. These are correctness runs,
not isolated performance measurements.

This changes delivery timing for safe batches; it is not native event-timing
parity. An event arriving during an older UI export can still wait for that
export. This stage neither reduces full-export CPU nor changes the snapshot
contents, UI revision policy, warnings or hidden widgets. Actual ready-command
latency and production-render parity require their own post-build receipts;
no before/after library speed ratio is claimed here.

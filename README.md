# KONTRA

KONTRA is a Rust sampler for instruments that use the Kontakt file format. It runs as a CLAP or VST3 plug-in and as a standalone application, using the MOOSE plug-in framework.

KONTRA is being built to give musicians an independent sampler, including native Linux playback of instruments they are entitled to use. The goal is interoperability and continued access to their musical work. It is not affiliated with, sponsored by, or endorsed by the owner of Kontakt. Compatibility remains incomplete: loading a preset does not establish that its controls, scripts, routing, or sound match Kontakt.

KONTRA supplies no commercial Kontakt instrument libraries. You supply your own instruments and samples; their licenses still apply. The source tree includes upstream NCW/WAV codec test fixtures and an openly licensed font, documented in [THIRD_PARTY.md](THIRD_PARTY.md).

**Licensing status:** project-authored code is Apache-2.0. Redistribution permission for the required vendored `ni-file` parser remains unresolved, and Native Instruments previously requested removal of its upstream repository. See the [licensing and interoperability review](docs/LEGAL.md) for sources and remaining questions.

Directly extracting plug-ins from the ZIP does not provide the DMG's offline ticket.

## Development and diagnostics

Windows editors use Direct3D 12 by default. Set `WGPU_BACKEND` before starting
the DAW to explicitly choose another compiled backend; startup failures do not
silently switch APIs. Renderer startup and the selected adapter appear in Logs
and retained support journals, including attempts recorded before GPU creation.

See [CONTRIBUTING.md](CONTRIBUTING.md) for development and validation guidance, and [CHANGELOG.md](CHANGELOG.md) for release changes. To report a problem, open the **Logs** tab, choose **Export support report…**, review the preview and new-folder destination, then choose **Export report**. The Logs tab works even when an instrument fails to import. Search or filter the retained events, then select an event for its stage, reason, source location and available load context.

The new report folder contains `report.json` with build/system/audio settings and load issues, `events.jsonl` with recent session events, and `journal.jsonl` with the current journal and retained inactive sessions from previous runs. The editor retains up to 2,048 events / 2 MiB; each active session rotates at 16 MiB total, and inactive journals are retained for up to 7 days / 64 MiB. Active sessions in other processes are excluded. Load summaries retain the first 1,024 distinct issue examples; `issues_omitted` counts further occurrences excluded from that summary. Off-thread load producers wait for capacity in the bounded journal queue, including records omitted from the summary. Other nonblocking event producers can still lose records under queue pressure; recorder drops, complete journal writes and write failures are separate counters. Counts identify omitted, truncated or unwritten events; a partial-journal warning means the available report was saved with coverage gaps. Export failures leave an explicitly incomplete bundle. Structured log paths are redacted by default, and those logs include bounded, numbered script excerpts around reported faults while excluding full script payloads, samples and credentials. The manual export also includes exact archived private crash originals and saved delivery records in `crash-evidence/`, with a per-file manifest labeling missing, active or incomplete sources. These private copies are **unredacted**, may contain sensitive native fields, and are unchanged by the structured-log redaction setting. Review them before sharing. It does not search OS crash-report directories or copy binary process dumps. Archived copies are never included in automatic uploads; automatic crash reports below exclude source excerpts altogether.

Confirmed host crashes are recovered on the next KONTRA load using BUFFR’s session markers, flight recorder, operating-system evidence and support transport. The captured sanitized report goes to the private support inbox; the linked public KONTRA issue contains platform, host, format, build and failure metadata. Library source excerpts, samples, access data, credentials and personal paths are excluded from automatic reports. Ordinary unclean exits are retained locally without being called crashes. They cannot block later confirmed incidents: earlier unconfirmed evidence is deferred privately and up to 32 deferred records are rechecked for late native confirmation per registration, with a cursor retained across launches. Other unselected stale sessions remain intact. Each incident has its own private `crash-reports/pending/<incident-id>.json` queue file, so different hosts cannot overwrite each other's reports. A registration reads up to 32 keyed files using a retained cursor, choosing the oldest confirmed incident in that batch before unknown evidence. Remaining reports survive exact-ID acknowledgement and are recovered on later registrations. Legacy `pending.json` is migrated on the worker only after its complete private raw original and manifest are durable; migration failure or cancellation retains the source. The report remains pending until the service acknowledges the complete evidence hash; failures appear in Logs and `last-report.json` in KONTRA’s local data directory. `KONTRA_DISABLE_NETWORK=1` keeps reporting local, and `KONTRA_REPORT_DIR` isolates report storage. Native evidence depends on the host/OS writing an accessible crash artifact; KONTRA does not install global signal, exception or Rust panic hooks.

Logs shows delivery status and the report ID, plus the public issue URL when the service supplies it. Selecting the event exposes those details for copying; a later launch restores the saved receipt. Unconfirmed sessions show that their evidence remains local. Recovered flight-recorder uploads include up to 128 startup records and 2,048 recent records. Longer journals explicitly report omitted slots, original size and BLAKE3 hash; the complete original is archived privately in local `crash-reports/originals` storage and remains after delivery. Archive failure preserves the session source. These originals have no automatic age/size pruning. Local JSON and native text reads buffer at most 8 MiB; oversized inputs are not partially parsed or used as crash confirmation. Complete oversized bytes and size/hash/status manifests are retained privately under `crash-reports/originals` when archival succeeds. An oversized pending report releases its slot only after that complete archival succeeds; it requires local support review instead of automatic upload. Native text views exceeding 1 MiB include explicitly labelled actual prefix/suffix bytes; oversized pretty JSON is omitted with an explicit partial-report notice. Matching native originals remain private, including unredacted OS fields, and are never automatically uploaded as raw files. Following [Apple’s crash JSON reference](https://developer.apple.com/documentation/xcode/interpreting-the-json-format-of-a-crash-report), `.ips` confirmation requires crash type `309`, the recorded PID/application and real exception metadata; explicit nonfatal/simulated reports are excluded. File modification times provide the existing incident-window filter; OS launch/capture timestamps remain in the evidence for review. Missing or unsupported evidence remains unconfirmed, and crash confirmation does not establish KONTRA fault ownership. Recorded queue drops and sequence gaps are included in the report; Windows binary dumps remain on the machine.

The support-service R2 backend privately stores the full submitted report, applies server-side redaction, expires that server copy after 30 days and publishes only a metadata summary. The reviewed service is deployed; a production host-crash-to-service roundtrip remains unverified. Complete unredacted local originals are retained for manual export. See [support provenance and privacy boundaries](src/support/SOURCE.md) for the inherited BUFFR mechanism and local queue/archive behavior.


For a native UI stall, launch the host or standalone with `KONTRA_NATIVE_UI_TIMING=1` in its environment, then drag a control. One ten-second capture appears as `native_frame_timing` in Logs and support exports. It measures application callbacks and presentation submission, including lock waits; it does not measure GPU completion or display FPS. Capture is disabled by default.

To load a snapshot, first load its base NKI, then use the instrument header menu → **Load snapshot…** or drop a `.nksn` onto that header. DAW state and KONTRA multis retain both source paths. Snapshots cannot open independently or target programs inside an NKM; the existing unsupported-state warnings still apply.

No broad compatibility area below is marked full.

## Build

Install Rust 1.99.0 (pinned in `rust-toolchain.toml`) and the pinned `cargo-moose` build tool. See [CI and snapshot checks](docs/CI.md) for the faster development profile and shipping verification:

```sh
cargo install --locked --git https://github.com/Matari-Audio/moose \
  --rev bffa4677d0b82119d38566ce7e932dc5c463d497 cargo-moose
```

On Linux, install the X11, OpenGL, Vulkan, ALSA, and JACK development packages. On macOS, install the Xcode command-line tools. On Windows, install Visual Studio Build Tools with the C++ workload.

```sh
cargo moose build --clap --vst3
cargo build --release --features standalone --bin kontakto-standalone
cargo run --release --bin kontakto -- inspect '/path/to/instrument.nki'
cargo run --release --bin kontakto
```

`cargo moose install --clap --vst3 --user` installs the plug-ins into user plug-in folders.

## Experimental REAPER migration

Inventory a project without changing it:

```sh
python3 tools/migrate_project.py '/path/to/song.RPP'
```

Save the desired instruments, routing and controls as a KONTRA `.kontra-multi`, then map each instance explicitly. Track and FX indices are zero-based. Build the CLI with its default plug-in feature, and prepare a ReaScript:

```sh
cargo build --release --bin kontakto
python3 tools/migrate_project.py '/path/to/song.RPP' \
  --map '0:0=/path/to/Strings.kontra-multi' \
  --output-copy '/path/to/song-kontra.RPP' \
  --reaper-script '/path/to/migrate.lua' \
  --state-exporter target/release/kontakto
```

Run the generated script in REAPER with the source project open and KONTRA VST3 installed. It creates a copy beside the source to preserve relative media paths, refuses existing output paths, verifies installed state after save/reopen, and writes a migration report. Unsupported mappings are reported; Kontakt's opaque state is not recovered. Review the report and listen to the copy before using it.
